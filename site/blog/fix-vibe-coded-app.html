How to fix a vibe coded app that broke after launch

By Manish Saraan, Founder & Principal Engineer, SortedLaunch. 10+ years of engineering, 50+ MVPs launched.Published 31 October 2026

To fix a vibe coded app, work from the most expensive failure to the least: back up the database and freeze deploys, inventory every external call, lock down data access and auth, make Stripe the source of truth for billing, add migrations, add error handling, then set up staging and backups. Most apps need targeted repair, not a rewrite. The audit takes 2 to 3 days and the repair usually fits a two-week sprint.

Why do vibe coded apps break after launch?

Vibe coded apps break after launch because AI coding tools optimize for a working demo, and a demo has one user, no money, and no bad actors. The code that handled your own clicks in a test account was never asked to handle two users editing the same record, a Stripe webhook that arrives twice, or a request with a forged ID in the URL. Those cases arrive within days of real traffic.

The pattern is consistent across the apps I have repaired. The frontend is usually fine. The problems sit in four places: data access rules, billing state, the database schema, and the absence of error handling around anything external. The tool wrote code that assumes every call succeeds, because during the build every call did.

The order you fix things in matters more than the tools you use. Fix the wrong thing first and you will spend a week polishing a feature while the database leaks customer data. The sequence below is the one I follow on every repair, from the most expensive failure to the least.

Step 1: Take a backup and freeze deployments

Before touching any code, take a full backup of the production database and store it somewhere that is not the same hosting account. On Supabase that is a dashboard export or pg_dump through the connection string. On a managed Postgres host it is a snapshot. On a hosted SQLite file it is a copy of the file. If the app stores uploads in a bucket, snapshot the bucket too.

Then stop deploying. Most vibe coded apps deploy automatically on every push to the main branch, which is convenient during the build and dangerous during a repair. Turn off auto-deploy, or point production at a fixed commit. You want every change from here to go through a pull request that someone reads.

If users are actively losing data or money right now, put up a maintenance page. A day of downtime is cheaper than a week of refunds. Founders resist this step, but no customer has ever churned over a maintenance page that said "back in a few hours", and several have churned over a duplicate charge.

Step 2: Find out what you actually have

You cannot repair a system you cannot describe. Spend half a day building an inventory before writing any fix. The list I produce in a scoping call covers:

  • Every external service the app talks to: database, auth provider, Stripe, email, file storage, AI model APIs, analytics. For each one, where the key lives and whether it has ever been rotated.
  • Every database table, who can read and write it, and which columns hold personal data or money.
  • Every route or API endpoint, and whether it checks who is calling it.
  • Every background job or scheduled task, and what happens if it runs twice.
  • The deployment path: which branch deploys, where environment variables live, and whether there is a staging environment at all.

Most of this can be found with grep. Search the codebase for process.env, fetch(, stripe., supabase.from(, and the name of your auth library. The AI tool scattered these calls across components because it had no reason to centralize them. Your inventory is also your first design document for the fix, because every place the same call appears is a place that will need the same correction.

Write the inventory down. If you later hire someone to do the repair, this document cuts the scoping time in half and the quote with it.

Step 3: Fix data access and authentication first

Data access is first because it is the failure that cannot be undone. A double charge can be refunded. A leaked customer list cannot be unleaked. Broken access control sits at the top of the OWASP Top 10, and in AI-generated apps it is the single most common problem I find.

The typical shape is this: the app uses Supabase or Firebase from the browser, the tables were created with row-level security disabled or with a policy that allows everything, and the "security" is the fact that the UI does not show other users' records. Anyone who opens the browser console and runs a query gets the whole table. Supabase documents row-level security clearly, but the generated code rarely enables it, because enabling it makes the demo fail until policies are written.

The fix, in order:

  1. Enable row-level security on every table that holds user data. Start with the table that holds the most sensitive data, not the easiest one.
  2. Write a policy per table that ties rows to auth.uid() or to a membership table for team accounts. Test each policy from a second user account, not from the admin dashboard.
  3. Move any operation that needs elevated permissions, such as sending email or charging a card, into a server-side function with the service key. The service key must never reach the browser bundle. Search the built JavaScript for it to be sure.
  4. Check every API route for an auth check at the top. Generated route handlers often read a user ID from the request body and trust it. Replace that with the ID from the verified session.
  5. Rotate every key that has ever been in a client bundle or a public repository, which in practice means all of them.

On the repairs I have done, this step is usually the longest part of the audit, because every table was readable by anyone with the anon key and each one needed its own policy and its own test from a second account.

Step 4: Make payments match what customers were promised

Billing is second because it is the failure customers notice fastest. The common defects in generated Stripe integrations are specific and repeat across apps:

  • The subscription status lives only in the frontend or in a column that is set at checkout and never updated. When a card fails or a customer cancels in the Stripe portal, the app keeps serving the paid plan.
  • The webhook endpoint exists but does not verify the Stripe signature, so anyone can post a fake "payment succeeded" event. Stripe's webhook documentation covers signature verification in a few lines, and the generated code skipped it.
  • Webhook handlers are not idempotent. Stripe retries events that do not return a 200 quickly, and a handler that credits an account on each receipt will credit it twice.
  • Trial logic is a date comparison in a React component. Changing the system clock extends the trial.

The repair is to make Stripe the source of truth for subscription state, with your database as a cache that only webhooks update. Verify the signature on every event, store the event ID and skip any you have seen before, and gate paid features on the cached status checked server-side. Then reconcile: pull every subscription from Stripe, compare against the database, and fix the mismatches by hand. This reconciliation routinely turns up customers still on the paid plan after cancelling, and sometimes paying customers locked out by a bug in the cancellation path.

Step 5: Repair the database schema and add migrations

Generated schemas tend to have a few shared problems: foreign keys that are missing, so orphaned records pile up; columns typed as text that should be numeric or timestamps; JSON blobs where a table was needed; and no migration history at all, because the AI tool ran raw SQL against the live database each time it changed something.

Introduce a migrations tool before changing anything. Supabase has its CLI, Prisma and Drizzle have their own, and plain SQL files with a version table work for everything else. Capture the current schema as migration zero. From that point on, every schema change is a file in the repository that runs the same way in staging and production.

Then fix the schema in small migrations, each reversible, each tested against a copy of the production backup from Step 1. Add the foreign keys with ON DELETE rules that match the business. Fix the column types, with a conversion that handles the bad data already in the column. Split the JSON blobs that the application queries into, because Postgres can index a column and cannot cheaply index a path inside a blob. Leave the JSON blobs that are only stored and returned.

Resist the urge to redesign. The schema does not need to be what you would have built. It needs to stop corrupting data and to be changeable next month.

Step 6: Add error handling and logging where the AI forgot

AI-generated code treats external calls as if they cannot fail. The email sends. The model responds. The file uploads. When one of these fails in production, the generated code either crashes the request or, worse, continues as if it succeeded and tells the user everything is fine.

Go back to the inventory from Step 2 and visit every external call. For each one, decide what should happen on failure: retry, fall back, queue for later, or show the user an honest error. Then implement that, and log the failure with enough context to debug it. A log line that says "error" is useless. A log line that says "stripe.customers.create failed for user 4812 with card_declined" is a support ticket answered before it is filed.

Set up a basic error tracker and a log drain. The free tiers of the common tools are enough for an app at this stage. For the first time you will be able to see errors you did not know you had, which is uncomfortable for a week and then becomes the way you run the product.

Step 7: Set up environments, deploys and backups

Most vibe coded apps have one environment, production, and deploy to it from the founder's laptop or on every push. Repairing them requires a staging environment, which means a second database, a second set of API keys in test mode, and a deploy path that goes laptop to staging to production.

The minimum setup I leave behind on every repair:

  • A staging environment with its own database and test-mode keys for every external service.
  • Environment variables managed in the host, with no .env file in the repository. Check the git history for one and rotate anything in it.
  • Deploys from a protected main branch, after a pull request, with the migrations running automatically before the new code starts.
  • Daily automated database backups with a tested restore. "Tested" means someone has restored one into staging and checked the data.
  • A health check endpoint and an uptime monitor pointed at it.

This step is boring, and it is the step that stops the next incident from being a disaster. It also makes the rest of the repair safer, because every fix from this point is tested on staging with a copy of real data before it reaches customers.

Step 8: Decide what to rewrite and what to keep

After the first seven steps the app is safe to run. Now you can look at the code quality with a clear head rather than in a panic. Most of it should stay. Generated React components are verbose and repetitive, but they work, and rewriting them produces no customer-visible improvement.

Rewrite the parts that fail one of two tests. The first test is whether a change in that area breaks something unrelated more often than not. That is the sign of logic that is duplicated across files, and it is cheaper to consolidate than to keep patching copies. The second test is whether the area blocks a feature you need in the next quarter. If the data model cannot represent teams and you need teams, the data model gets rebuilt now, while the app is small.

Everything else goes on a list with a rough cost, and the list waits until the business asks for it. The goal of a repair is a product you can keep shipping, not a codebase you are proud of.

How long does fixing a vibe coded app take?

For an app with a few hundred users and a simple billing model, the audit takes 2 to 3 days and the repair fits in a two-week sprint. For apps with multi-tenant data, a mobile client, or a marketplace with payouts, the repair runs the full four-week build. When should you hire someone to fix a vibe coded app?

Hire when the app takes money, holds personal data, or has more users than you could email personally if something went wrong. Below that line, the steps above are a reasonable weekend project for a founder who can read code, and the inventory alone will teach you a great deal about what you built.

Above that line, the cost of a mistake in Step 3 or Step 4 exceeds the cost of the repair. A locked-out customer base or a leaked table is a company-ending event for an early product. Someone who has done this many times will also know which of the generated patterns are harmless and which are time bombs, which saves the week you would otherwise spend fixing things that did not need fixing.

Whichever route you take, do Step 1 today. The backup costs nothing and it is the only step that cannot be done after the fact.

Frequently asked questions

Can I fix a vibe coded app myself without a developer?

You can do the first three steps yourself: take a database backup, freeze deployments, and inventory what the app connects to. Fixing data access rules and payment logic needs someone who can read the code, because a mistake there locks users out or double-charges them. Many founders do the inventory themselves and then hand over a focused brief, which keeps the repair cost down.

Should I rewrite my vibe coded app from scratch?

Rarely. In the repairs I have done, most of the generated code was usable once the data layer, auth, and billing were fixed. A rewrite makes sense when the schema cannot represent your business, when the framework choice blocks a core feature, or when the code is so tangled that each fix breaks something else. The scoping call is where that decision gets made with the code open.

How long does it take to fix a vibe coded app?

For a typical app with a few hundred users, the audit takes 2 to 3 days and the repair fits a two-week sprint. Apps with payments, multi-tenant data, or a mobile client can take the full four-week build. A fixed quote and date come out of the scoping call before any work starts.

Which AI coding tools produce the most problems?

The tool matters less than how it was used. Lovable and Bolt apps tend to ship with overly permissive database rules because the tools favor getting a demo working. Cursor and Replit apps vary with the prompts the founder wrote. The repair steps in this guide apply to all of them.
